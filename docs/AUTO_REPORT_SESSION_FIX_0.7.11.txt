REPRODUCED CODE DEFECT
0.7.10 records native session-update IDs only inside its active capture. A capture
with no opponents is discarded immediately at combat end, taking those IDs with
it. If catalog insertion lags behind the update/end event, the immediate baseline
can omit that completed session. Once it appears alongside the next PvP session,
verification sees two "fresh" sessions and rejects the encounter. An idle update
can also precede catalog insertion and be lost by the baseline refresh.

A regression fixture reproduces this order and fails against 0.7.10. The live
export records neither candidate IDs nor meter-update events, so it cannot prove
that this exact ordering caused either of the two multi-session rejections.
It also cannot isolate the missing damage field in the single-session rejection.

CORRECTION
Keep the last 64 distinct readable session-update IDs in a bounded ring and set,
including NPC/cooldown captures and idle updates. At capture start, copy the
out-of-combat catalog baseline and those prior IDs into a frozen baseline (at
most 128 IDs). Updates during the capture never change that baseline. A meter
notification that first reveals combat still starts the capture BEFORE recording
its ID, so it remains eligible as current-fight evidence. Clear history on native
meter reset and addon initialization. This history fix adds no polling timer or
combat meter read; the separate activity feature adds a five-second combat check.

Truly multiple new sessions still fail closed. Never pick the newest/largest
session or reuse an earlier fight's damage. NPC/pet flags, positive per-unit
amounts, observed opposing-player identities, fresh session correlation, combat/
lockdown gates, duel/instance/FFA exclusions, cooldown and one attempt remain.

The journal now logs each capture's first update per session, whether it was in
the baseline, fresh IDs (up to eight), correlation count and catalog readability.
Failed attribution logs the category and source/details failure, or row counts
rejected for NPC, pet, unavailable flags/name, unseen/ambiguous name, or invalid/
nonpositive amount. Each row has one rejection reason; these are counts, not
proof that no damage occurred. Existing three-read and export bounds remain.
Bindings.xml declares its category once while retaining all four actions.
